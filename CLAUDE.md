# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm start` — launch the Electron app (runs `electron .`).
- `npm run build` — production Windows build (`electron-builder --publish never --win --x64`). Runs `prebuild` first via the `prebuild` npm lifecycle script (`node prebuild.js`).
- `npm run build-portable` — portable Windows build.
- `npm run check` / `node prebuild.js` — the closest thing to a lint/preflight step. Verifies `bin/` binaries (yt-dlp, ffmpeg, ffprobe) exist and aren't truncated, verifies `stems.py`/`analyze.py`/`installer/setup-engines.ps1`/`key_model.pkl` are present and not placeholders, then SHA-256-hashes every file in `integrity.js`'s `PROTECTED_FILES` list and writes `manifest.sha256.json`. The app reads this manifest at startup (`integrity.js`'s `verifyIntegrity`) and refuses to start the engine layer if a protected file's hash doesn't match — so editing `server.js`, `main.js`, `preload.js`, `stems.py`, `analyze.py`, or `_phull_internal.py` in a built/packaged copy requires re-running `node prebuild.js` (or a full `npm run build`) to regenerate the manifest, or the packaged app will report tampering.
- `bash gauntlet.sh` — the project's test suite. Not a standard test runner: it's a single ~1300-line script combining `node --check` syntax validation, Python `ast.parse` validation, static regex/AST regression guards against specific historical bugs (i18n key parity, route-registration order, packaging sanity, etc.), and numeric DSP checks via `node tools/test-*.js`. Run this after any change to `renderer/app.js`, `server.js`, `renderer/index.html`, or the worklet files. It uses `set -e`, so it stops at the first failure — read the failing PASS's label to find which guard tripped.
- Run a single DSP test: `node tools/test-autotune.js` (pitch detection + `PitchShifter`), `node tools/test-autotune-processor.js`, `node tools/test-detect-key.js`, `node tools/test-rb-channel-safety.js`, `node tools/test-rb-graph.js`, `node tools/test-rb-recorder.js`. Each extracts a marked `CORE` section from its corresponding worklet/`app.js` region via `vm.createContext`/`vm.runInContext` and exercises it with synthetic signals — no browser or Electron runtime needed.
- `python3 tools/xref.py` — cross-references a fixed file list (`server.js`, `main.js`, `updater.js`, `sentry-init.js`, `preload.js`, `updater-preload.js`, `lib/impulse.js`, `renderer/app.js`, `renderer/daw.js`) for calls to undefined helpers. Invoked automatically by `gauntlet.sh`.
- `npm run audit` — `npm audit --omit=dev`.

There is no separate lint command (no ESLint/Prettier config in the repo) — `gauntlet.sh`'s `node --check` calls and `tools/xref.py` are the syntax/reference safety net.

## Architecture

**Process split.** `main.js` is the Electron main process: it forks `server.js` as a child process (an Express server bound to `127.0.0.1:47891`) and opens one or more `BrowserWindow`s — the main app window plus a separate branded updater window (`updater.js`/`updater-preload.js`). `preload.js` exposes a narrow `window.api` surface via `contextBridge`; all main-process capabilities (window controls, file pickers, drag-out, temp-wav writing, log path, relaunch, updater control) go through the ~14 IPC channels registered with `ipcMain.handle`/`ipcMain.on` in `main.js` — there is no `nodeIntegration` shortcut into the renderer.

**Backend is a real local server, not just IPC glue.** `server.js` (~7.4k lines) is a full Express app with ~90 routes covering download (yt-dlp wrapper with SSE progress), analysis, stem separation, transcription, mastering, stockpile (library/tagging), history (SQLite via `sql.js`, held in memory and debounce-persisted to disk), and a `/events` SSE channel used to keep multiple clients — the Electron window and the companion Chrome extension (`extension/`) — in sync against the same backend process. Because the renderer talks to this backend over plain HTTP/SSE rather than IPC for most features, changes to renderer data flows usually mean touching a `server.js` route, not `main.js`.

**Python engine layer runs as spawned child processes, not embedded.** `analyze.py` (BPM/key/loudness, using a bundled `key_model.pkl` ML model with an algorithmic Krumhansl fallback), `stems.py` (AI stem separation), `mastering.py`, `fingerprint.py`, `write_tags.py`, and `_phull_internal.py` are invoked via `spawn(pythonCmd, ...)` from `server.js`. `discoverPython()` (server.js) resolves an interpreter with a strict priority order — a private embedded runtime under `%LOCALAPPDATA%/freqphull/engines/python` (only trusted once it actually has `numpy` installed) beats a marker file from `installer/setup-engines.ps1`, which beats the Windows `py` launcher, which beats common install-path probing — and caches the result for 10 minutes. `/engines/verify`, `/engines/repair`, `/engines-status`, and `/setup-engines` (SSE-driven) routes in `server.js` drive first-run provisioning via `installer/setup-engines.ps1`. When touching anything in the engine-bootstrap path, `clearPythonCache()` must be called or a stale interpreter path will stick for up to 10 minutes.

**Build-time integrity manifest.** `prebuild.js` (run before every build) SHA-256-hashes the files listed in `integrity.js`'s `PROTECTED_FILES` (`server.js`, `main.js`, `preload.js`, `stems.py`, `analyze.py`, `_phull_internal.py`) into `manifest.sha256.json`. At runtime, `verifyIntegrity()` recomputes those hashes and refuses to start the engine layer on a mismatch (a "tampered" status), while missing-manifest (e.g. dev builds) is treated as a soft failure. `UNPACKED_FILES` in `integrity.js` handles the fact that `asarUnpack`'d files live outside `app.asar` at a sibling `app.asar.unpacked/` path in a packaged build — if you add a new protected file that's also `asarUnpack`'d, it needs to go in both `PROTECTED_FILES` and `UNPACKED_FILES`, or hashing will silently look in the wrong place.

**Renderer is intentionally flat, not modular.** `renderer/app.js` (~20k lines) and `renderer/index.html` (~4.9k lines) hold essentially all UI logic and markup for every tab (`tab-analyze`, `tab-download`, `tab-history`, `tab-random`, `tab-settings`, `tab-slowverb`, `tab-stems`, `tab-stockpile`, `tab-tools`, `tab-transcribe`), switched via `showTab(btn)`. Global state and functions are namespaced by informal prefix rather than by module: `rb*` for the Topliner/Random-Beats vocal recording+autotune feature, `sep*` for the stem separator, `sp*` for Stockpile library organization. `renderer/daw.js` is a separate mini-DAW module loaded alongside it. `lib/impulse.js` holds small shared helpers. There's no bundler step — these files are loaded directly by `index.html`, so new code is added in place within the relevant prefix's region rather than as a new module.

**DSP lives in AudioWorklets, tested headlessly via marker-delimited CORE sections.** `renderer/autotune-worklet.js` (pitch detection + PSOLA-style pitch shifting + LPC formant correction), `renderer/rb-recorder-worklet.js` (lossless PCM capture), and `renderer/rb-channel-safety-worklet.js` (mic-channel selection/debounce, used unconditionally in both the record and monitor audio graphs) each wrap their pure DSP logic in `// ─── BEGIN X CORE` / `// ─── END X CORE` marker comments. The corresponding `tools/test-*.js` scripts extract just that marked region via Node's `vm` module and run it against synthetic signals outside of any AudioWorkletGlobalScope — this is how DSP correctness is verified without a browser. The same pattern appears inside `renderer/app.js` itself for two Random Beats sections: `BEGIN/END RB DSP PARAM MATH` (gain/reverb parameter mapping) and `BEGIN/END RB GRAPH DSP CORE` (Random Beats Graph Mode pitch-editing), tested by `tools/test-rb-graph.js`. When modifying DSP, keep new logic inside the existing marker block (or add a new clearly-delimited one) so it stays extractable and testable — logic that reaches out to instance/worklet-only state (e.g. `this.port`, `currentFrame`) breaks the extraction.

**Packaging.** electron-builder targets Windows (nsis + portable) with `asar: true`; `bin/` binaries, Python scripts, `key_model.pkl`, `installer/setup-engines.ps1`, `extension/`, and `assets/icon.ico` are copied via `extraResources`/`asarUnpack` since Python needs real on-disk files, not asar-packed ones. `electronVersion` is pinned to match the `electron` devDependency. Releases publish to GitHub (`CodePhull/FreqPhull-realease`) via `electron-updater`, checked on launch with both an inline banner and the dedicated updater window.
